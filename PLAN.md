# Plan

The order of work toward [SPEC.md](SPEC.md). Measurement comes first, so every later change can be judged by the [principles](contributing/principles.md). Then cost and quality, then configuration, then user features. Numbers in parentheses are spec sections.

## Phase 1: Measurement

Goal: know what a review costs, where the money goes, and how good it is.

- [x] **Headless harness (9).** Replace the Agent SDK with a `claude -p` profile: read-only flags, the guard hook passed with `--settings`, isolated sessions, `--json-schema` output, and usage parsing. Done when: the tests pass and a run on the same diff gives similar findings, with cost and time recorded.
- [x] **Call records (10).** `calls.jsonl` with tokens (input, cache read, cache write, output), cost and cost source, and time per call. Per-step and per-run totals in `run.json`. Done when: `run.json` shows cost and time per step.
- [x] **Cursor harness and computed cost (9, 10).** An `agent -p` profile with read-only flags, a tool-call check after the fact, JSON parsing with one repair turn, and token parsing. A dated price table gives `computed` cost from tokens. Default model is Grok 4.7 low. Done when: a Cursor run on the Claude comparison diff records cost and time per step.
- [x] **Run index (10).** `index.jsonl`, `review-flow runs`, and `review-flow compare`. Done when: `compare` shows per-step cost and time and the finding differences between two runs.
- [x] **Eval dataset (11).** 25 bug cases and 10 clean cases mined from 19 small repos with a one-off script, 8 marked as the smoke set, in our own format with source and license noted ([eval/](eval/README.md)). Done when: the dataset is in the repo with its source and license noted.
- [x] **Eval command (11).** `review-flow eval [--smoke]` keeps its own checkout per case repo, runs the pipeline with each case's base and head, and scores recall (same file, overlapping lines, small tolerance), findings per clean case, cost, and time. Results are saved as an eval run. Done when: `compare` works on two eval runs.
- [ ] **Baseline.** Run today's pipeline 3 times on the full set. Done when: the mean and spread are in the decision log.

## Phase 2: Cost and quality

Goal: the same or better quality for less money. Each item follows the acceptance rule below and ends with an entry in the decision log.

- [ ] **Finding model (5).** Origin, `unverified`, severity set by the verifier, and `pre-existing.json`. Scoring ignores pre-existing findings. This changes what is scored, so the baseline is run again (3 times) afterward.
- [ ] **Cheaper verifier.** Try a cheaper model or lower effort for verifiers.
- [ ] **Batched verifiers (4).** Batch findings by file group, send the diff once per batch, and verify the highest severity first.
- [ ] **Dedupe (4).** Merge findings with the same root cause, including bug classes across files.
- [ ] **Filter (4).** Drop style, cleanup-only, and diagnostic findings. Judged mainly on the clean cases.
- [ ] **Finder sharding (4).** Split large diffs into file groups, one finder each.

### Acceptance rule

1. Iterate on the smoke set, then confirm on the full set. Run 3 times when the result is close to the baseline spread.
2. A **cost change** is accepted when recall stays within the baseline spread, findings per clean case don't rise beyond it, and cost or time drops.
3. A **quality change** is accepted when recall or findings per clean case improve beyond the spread. Its extra cost is stated in the log.

## Phase 3: Configuration and defaults

Goal: zero-config reviews that are good by default, with overrides for everything else.

- [ ] **Config files (8).** JSONC user and project files, env vars, flags, `--config`, strict validation, `$schema`, `review-flow config`, and `config set`.
- [ ] **Presets (8).** `quick`, `standard`, and `deep`, with values from phase 2. `deep` adds finder focus areas and verifier voting, each checked with an eval.
- [ ] **Budgets (8).** Money and time limits, the pre-flight estimate, the graceful stop, and the unknown-cost warning.
- [ ] **Exit codes (7).** `failOn` and exit codes `0` to `4` and `130`.
- [x] **Base detection (2).** Fetch `origin/main` or `master`, prompt in a TTY, and fall back to local.
- [ ] **Default harness (9).** Detect installed CLIs and remove the required `--harness` flag. Done so far: a TTY run asks for the harness and saves it to the user config.

## Phase 4: User features

Goal: cover how developers actually review, in order of usefulness.

- [x] **Summary (4, 7).** A Summarize step in parallel with Find, on by default: goal, changes, how well the goal is met (gaps and extras), and where to look. Printed before the findings, saved as `summary.json`, and used as the posted review body. `--no-summary` skips it; `review-flow summary [target]` runs it alone. Done when: a review prints the summary before the findings, and its extra cost and time are in the decision log, measured on the smoke set.
- [ ] **Worktree (4, 10).** Review in a disposable worktree. Done so far: `.review-flow/` has its own `.gitignore`, and the root `.gitignore` is no longer edited; PR targets are reviewed in a worktree.
- [ ] **Targets (2).** Branch, commit, `a..b`, and `a...b` targets. Done so far: uncommitted changes through a snapshot commit.
- [ ] **Distribution (12).** The npm package `review-flow` and `review-flow doctor`. Done so far: the bundled package and `pnpm release`.
- [x] **PR targets and trust (2, 3).** PR number or URL, trust levels and their policies, and `--trust`. `trust` rules in config come with config files; reading `REVIEW.md` and repo config from the base comes with them and the review guide.
- [ ] **Posting (7).** `review-flow post` with selection, editing, the stale-head check, preview, and a `COMMENT` review. Done so far: all but editing in `$EDITOR`.
- [ ] **Questions (7).** `review-flow ask [run]`: a question loop in a worktree at the reviewed SHA, the next-step menu after a review, `asks.jsonl`, and `ask --open` to hand off to the interactive CLI. Done when: a follow-up question on a PR run is answered with code references, and the cost per question, cold and warm, is in the decision log.
- [ ] **Review guide (8).** `REVIEW.md`, read from the base for untrusted targets.
- [ ] **Incremental reviews (6).** Interdiff focus, follow-up of earlier findings, repeat suppression, and response records.
- [ ] **More harnesses (9).** A `codex` profile, user-defined profiles, and price-table overrides (`prices`).
